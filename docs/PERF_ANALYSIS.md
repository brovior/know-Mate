> 것이다. 확정 계약은 `docs/DESIGN.md`, 현재 단계는 `docs/ROADMAP.md`가 정본이다.

## 0. 결론 먼저

개선 여지는 **있다**. 다만 성격이 둘로 갈린다.

| 구분 | 내용 | 판단 |
|---|---|---|
| 즉시 착수 가능 | 불필요한 DB 조회·전 컬럼 로드 제거 (§2) | 근거가 코드에 있음. 실측 없이도 착수 가능 |
| 실측 선행 필요 | 파이프라인 병렬화·배치 재설계 (§3) | 미해결 20초 이슈의 원인을 가릴 위험. `docs/ROADMAP.md` 실측 대기 항목 해소 후 |
| 규모 선행 필요 | 벡터 인덱스 (§4) | 현재 문서량에서는 체감 없을 수 있음. 5b 공용DB 전에는 필수 |
| 체감 전용 | 쿼리 비동기화·LLM 스트리밍 (§5) | 처리량이 아니라 체감 지연을 바꾼다. `docs/ISSUE_B_query_async.md` 선행 |

**가장 먼저 할 것**: §2. 이유는 (a) `CLAUDE.md §2-2` 불변식 위반을 겸해서 고치는 것이고,
(b) 동시성 모델을 건드리지 않아 회귀 위험이 낮으며, (c) 미해결 20초 이슈의 계측을 방해하지 않는다.

## 1. 현재 파이프라인 구조 (사실)

### 인덱싱 (쓰기)

`collector/scheduler.py`의 `_run_cycle`은 생산자 1 + 소비자 1 구조다.

- 생산자 스레드: 폴더 순회 → 변경 판정 → 백오프·DRM 판정 → `PriorityQueue` 적재. **스캔만 한다.**
- 소비자(워커 스레드 본체): 큐에서 하나씩 꺼내 **추출 → 청킹 → 임베딩 → 암호화 → `table.add()`**
  를 한 파일씩 순차 수행한다.

즉 추출(로컬 CPU·COM)과 임베딩(네트워크 대기)이 **완전히 직렬**이다. 한쪽이 도는 동안 다른
쪽은 논다.

### 검색 (읽기)

`rag/retriever.py`의 `search()`는 한 질의에 대해 테이블 검색을 **최대 3회** 수행한다.

1. `chunks` 벡터 검색
2. `chunks` 키워드 보강 검색 (`file_path LIKE '%토큰%'` 최대 5개 OR)
3. `emails` 벡터 검색

이후 `llm.answer()`가 응답 전체를 받을 때까지 블로킹한다(`llm/client.py`, `timeout=60`).
`bridge.sendQuery`는 이 전체를 **메인 스레드에서 동기 실행**한다.

## 2. 즉시 착수 가능 — 불필요한 DB 작업 제거

`CLAUDE.md §2-2`는 "LanceDB 조회는 필요한 컬럼만 `search().select([...]).to_arrow()`로
가져온다. `select()` 없는 전체 `to_arrow()` 호출은 금지한다"고 규정한다.
`app/bridge.py`와 `collector/purge_meta.py`는 이 규칙을 지키지만, **아래 5곳은 지키지 않는다.**

| # | 위치 | 호출 빈도 | 불필요하게 읽는 것 |
|---|---|---|---|
| 2-1 | `collector/mail_scanner.py` `_source_index_state` | 메일 파일 1건당 1회 | 전 컬럼(1024차 vector + 암호화 본문) |
| 2-2 | `rag/email_indexer.py` `is_indexed` | 메일 파일 1건당 1회 | 전 컬럼 |
| 2-3 | `rag/retriever.py` `_search_table` | 질의 1건당 최대 3회 | vector 컬럼 |
| 2-4 | `rag/indexer.py` `delete_chunks` | 수정된 문서 1건당 1회 | vector + text |
| 2-5 | `collector/cleanup.py` `_check_physically_deleted` | 삭제 확인 1회당 | vector + text |

### 2-1·2-2가 특히 크다 (가설)

`run_mail_scan`은 후보 메일마다 DB를 **두 번** 조회한다 — `_source_index_state`(source_file
기준)와 `is_indexed`(mail_uid 기준). `max_mails_per_scan` 기본값이 500이므로, **이미 전부
인덱싱이 끝난 정상 상태에서도 스캔 사이클마다 최대 1000회의 필터 조회**가 발생하고, 각 조회는
전 컬럼을 파이썬으로 끌어온다. 벡터 1개가 1024×4바이트이므로 행당 최소 4KB다.

개선 방향: 사이클 시작 시 `select(["source_file", "mail_uid", "mtime", "source_meta"])`로
**한 번** 읽어 메모리 dict를 만들고, 파일별 판정은 dict 조회로 끝낸다. 조회 횟수가 N → 1이 된다.

- 상충: 메일 수가 매우 많으면 dict가 메모리를 점유한다. `mail_uid`·`source_file`은 문자열이라
  벡터보다는 훨씬 작지만 상한이 필요하다.
- 미측정: 실제 메일 건수와 조회 1회당 소요시간을 재지 않았다. **이 항목의 효과 크기는 가설이다.**

### 2-4의 부수 문제

`delete_chunks`는 `chunk_id IN ('...', '...')` 문자열을 청크 수만큼 만든다. 파일당 청크 상한이
500(`max_chunks_per_file`)이므로 최악의 경우 UUID 500개짜리 SQL 문자열(약 19KB)이 만들어진다.
같은 문자열이 `search().where()`, `update(where=)`, `delete()`에 최대 3번 쓰인다. 배치 분할이 필요한지
검토 대상이다. **미측정.**

## 3. 실측 선행 필요 — 인덱싱 파이프라인

### 3-1. 추출과 임베딩의 겹치기

현재 소비자 하나가 추출·임베딩을 직렬로 수행한다(§1). 임베딩은 `http.client` 대기 구간이라
GIL을 놓으므로, 스레드를 하나 더 두면 **파일 A의 임베딩과 파일 B의 추출이 겹친다.**
직렬 합(추출+임베딩)이 최대값(max)에 가까워진다.

제약(반드시 지켜야 하는 것):
- LanceDB 쓰기는 한 스레드로 유지한다. `CLAUDE.md §2-3`이 `multiprocessing`을 금지한 이유가
  파일 잠금 충돌이며, 스레드 동시 쓰기도 같은 위험이다.
- COM 추출은 스레드 친화성이 있다. 추출은 현재 스레드에 그대로 두고, **임베딩+저장만** 뒤로
  넘기는 방향이어야 한다.
- 파일 단위 실패 격리(`CLAUDE.md §2-3`)가 깨지면 안 된다. 현재 예외 처리·`failure_state`
  기록·워치독 무장/해제·`com_restart_every_n_files` 카운팅이 전부 소비자 루프 한 몸에 있다.
- "처리 중 파일 변경" 검사(`stat` 재확인)는 임베딩 직전에 있어야 의미가 있다. 뒤로 넘긴
  스레드에서 다시 확인해야 하는지 판단이 필요하다.

**착수 시점 논쟁거리**: `docs/ROADMAP.md`의 미해결 항목 중 "임베딩 파일당 ~20초 고정 비용"이
아직 원인 미상이다. 병렬화를 먼저 하면 20초가 다른 작업 뒤에 숨어 **원인 규명이 더 어려워진다.**
계측 데이터로 원인을 가른 뒤에 착수하는 것이 맞다고 본다 — 이 판단 자체가 교차검증 대상이다.

### 3-2. 임베딩 배치가 파일 경계에서 끊긴다

`Indexer.index_file`은 `batch_size`(기본 32) 단위로 임베딩하지만, **배치는 한 파일 안에서만
묶인다.** 청크 3개짜리 파일은 청크 3개로 API를 1회 호출한다.

호출당 고정비가 크다면(현재 20초 이슈가 정확히 이 모양이다) 파일 간 청크를 모아 32개를 채워
보내는 편이 호출 수를 크게 줄인다.

- 상충: `index_file`의 "파일당 `add()` 1회" 원칙(LanceDB fragment 누적 방지)과, 파일 단위 실패
  격리가 배치 경계와 어긋난다. 임베딩 배치 경계와 저장 트랜잭션 경계를 분리하는 설계가 필요하다.
- **20초의 원인이 호출당 고정비가 아니라면 이 변경은 효과가 없다.** §3-1과 같은 이유로 실측 선행.

## 4. 규모 선행 필요 — 벡터 인덱스

**코드 전체에 `create_index` 호출이 없다.** LanceDB는 벡터 인덱스가 없으면 전건 스캔(flat
search)으로 동작하므로, 검색 1회 비용이 전체 청크 수에 **선형**으로 증가한다. 질의당 최대 3회
스캔하므로(§1) 계수도 3이다.

- 현재 개인 PC 문서량에서는 체감되지 않을 수 있다. **미측정.**
- `docs/ROADMAP.md`의 5b(공용 벡터DB, 복사 배포)가 들어오면 청크 수가 개인 PC 규모를 넘어선다.
  **5b 착수 전에는 결론이 나 있어야 한다.**
- 상충: LanceDB의 IVF_PQ 인덱스는 근사 검색이라 재현율(recall)이 떨어진다. 현재는 `top_k*2`
  후보만 뽑아 점수 문턱으로 거르므로 후보가 얕고, 근사 오차가 결과 품질에 바로 드러난다.
  인덱스 도입 시 후보 수 상향이나 refine 단계가 같이 필요하다.
- 상충: 인덱스는 데이터가 늘면 재생성해야 한다. 증분 인덱싱이 상시 도는 이 앱에서 재생성
  시점을 언제로 잡을지가 별도 설계 문제다.

### 4-1. 키워드 보강 검색

`_keyword_where`가 만드는 `file_path LIKE '%토큰%'`는 인덱스를 탈 수 없어 항상 전건 스캔이다.
질의마다 무조건 1회 발생한다. 파일 경로 목록은 이미 `bridge.py`가 projection으로 싸게 읽는
방식을 쓰고 있으므로, 경로 목록을 메모리에 캐시해 후보를 좁히는 대안이 있다. **미측정.**

## 5. 체감 지연 — 처리량과 별개

### 5-1. 쿼리 비동기화

`docs/ISSUE_B_query_async.md`에 위험 분석까지 끝난 채 보류 중이다. 처리 속도를 바꾸지 않지만
"창이 얼어붙는" 체감을 없앤다. 이 문서는 새 근거를 더하지 않는다 — 기존 판단을 따른다.

### 5-2. LLM 응답 스트리밍 없음

`llm/client.py`의 `answer()`는 응답 **전체**를 받은 뒤 한 번에 반환한다. 사용자는 첫 글자까지
전체 생성 시간을 기다린다. 토큰 스트리밍으로 바꾸면 실제 처리 시간은 그대로여도 체감 대기가
첫 토큰까지로 줄어든다.

- 선행 조건: §5-1이 없으면 스트리밍해도 메인 루프가 막혀 화면이 갱신되지 않는다. **순서가 있다.**
- 미확인: 사내 LLM API가 SSE 스트리밍을 지원하는지 확인하지 않았다. **가설.**

### 5-3. 첫 질의 지연

`KnowledgeAgent`는 첫 질의 시점에 `_build_pipeline()`으로 Indexer·EmailIndexer·Retriever·LLM을
한꺼번에 만든다(LanceDB connect 2회 포함). 이 비용이 첫 질의에만 얹힌다. 앱 시작 후 유휴 시점에
미리 만들어두는 선택지가 있다. **미측정.**

## 6. 이 문서가 다루지 않은 것

- COM 추출 자체의 속도(DRM ppt open 편차). `docs/ROADMAP.md`의 계측 대기 항목이며 원인이
  앱 밖에 있을 가능성이 커 이 분석의 범위 밖이다.
- 실측 수치 전반. 이 문서의 모든 효과 추정은 코드 구조에서 나온 가설이고, 어느 항목도
  프로파일링으로 확인하지 않았다.
- 메모리 사용량. 과거 개선 이력(`docs/UPDATE_NOTES.md` 2026-07-24·25)이 있으나 이번에 재확인하지 않았다.

## 7. 교차검증에서 특히 다투고 싶은 것

1. §2를 먼저 하고 §3을 실측 뒤로 미루는 순서가 맞는가. 아니면 §3-1을 먼저 해서 20초를 상쇄해
   버리는 편이 사용자에게 이득인가.
2. §3-1의 "임베딩+저장만 뒤로 넘긴다"가 파일 단위 실패 격리·워치독·COM 재기동 카운팅을 깨지
   않고 가능한가. 깨진다면 어디서 깨지는가.
3. §4의 벡터 인덱스를 5b 전에 넣을 근거가 충분한가. 근사 검색 도입이 현재의 얕은 후보 수
   (`top_k*2`)와 점수 문턱 설계와 양립하는가.
4. §2-1의 "메모리 dict로 전환"이 메일 건수 상한 없이 안전한가.
5. 빠뜨린 병목이 있는가. 특히 청킹(`rag/chunker.py`)과 암호화(`secure/crypto.py`)는 이번
   분석에서 비용을 따지지 않았다.
