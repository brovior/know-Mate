## 총평
불필요한 벡터·암호문 로드를 단일 컬럼 projection으로 교체하고, 성공·실패·차단 상태를 분리한 조건부 스킵을 도입한 방향은 타당하다. 특히 보수적인 메타 손상 처리, 실패 후 성공 서명 해제, 대량삭제 fail-closed 정책은 재실행 안전성과 삭제 안전성을 잘 고려했다. 다만 실측한 버전은 0.34.0뿐인데 배포 범위를 0.34.x 전체로 허용하면서 이를 “재현성”과 “실측 검증 범위”로 설명한 부분은 호출 규약 비호환 방어 논리와 맞지 않는다. 또한 unsupported 억제 키가 실제 capability가 아닌 버전 문자열 중심이어서 동일 버전 재설치로 환경이 복구되어도 억제가 풀리지 않을 수 있으므로 변경이 필요하다.

**판정**: REQUEST_CHANGES

## 동의하는 결정
- `table.search().select(["file_path"]).to_arrow()`로 projection하고 pandas 변환까지 제거한 결정에 동의한다. 기존 병목의 직접 원인인 벡터·암호문 로드를 제거하면서 변경 범위도 purge 조회 경로로 제한된다.
- 성공 스킵보다 차단·백오프 판정을 먼저 수행하고, 일시 실패 및 unsupported 전이에서 `reconciled_sig`를 해제하는 상태 전이에 동의한다. 이전 성공 상태가 재시도를 최대 24시간 가로막는 문제를 방지한다.
- sidecar 손상·부재를 “스킵 불가”로 처리하고 purge를 보수적으로 재실행하는 정책은 적절하다. 삭제 작업의 멱등성을 활용하면서 기존 `index_state.json` 소비자에 대한 마이그레이션 위험도 피한다.
- `max_delete_ratio` 비정상 값을 기본 삭제율로 조용히 대체하지 않고 사실상 삭제를 차단하는 fail-closed 정책에 동의한다.
- 성능 시험을 독립 프로세스와 독립 DB 복제본으로 수행하고, 반환 행 수와 삭제 후보 완전성까지 함께 검증하는 계획은 측정 오염과 기능 회귀를 모두 고려한 합리적인 접근이다.

## 지적 사항

### [M-1] 허용한 LanceDB 범위가 실제 검증 범위 및 재현성 주장과 불일치 (Major)
- **관점**: 2. 숨은 가정, 8. 장애 대응
- **지적**: `lancedb>=0.34.0,<0.35`는 정확한 버전 고정이 아니며, 문서에서 실측한 0.34.0 외의 0.34.x 릴리스도 빌드 시 선택될 수 있다. 따라서 이를 “빌드 재현성” 및 “실측 검증 범위”라고 부를 근거가 부족하다.
- **근거**: ADR과 A-0002는 호출 규약 비호환을 서킷 브레이커 없이 버전 고정과 시작 시 검사로 예방한다고 설명한다. 그러나 검사 역시 같은 범위 전체를 정상으로 인정하므로, 0.34.1 이상의 API 또는 동작이 달라져도 진단을 통과하고 purge가 30분마다 실패하는 상태에 들어갈 수 있다. 문서에 제시된 projection 실측 결과는 명시적으로 lancedb 0.34.0에서만 확보됐다.
- **대안**: 배포용 의존성을 검증된 정확한 버전으로 고정하고 가능하면 해시 기반 lock을 사용한다. 0.34.x 범위를 유지해야 한다면 허용하는 각 버전에 projection 계약 테스트를 CI에서 실행하고, 성공한 버전만 allowlist로 관리해야 한다. 문서의 “재현성” 표현도 실제 잠금 방식에 맞게 수정한다.

### [M-2] unsupported 억제 키가 실제 capability 복구를 식별하지 못함 (Major)
- **관점**: 7. 동시성, 8. 장애 대응
- **지적**: `compute_capability_sig()`가 lancedb 버전·앱 버전·projection 전략 버전만 포함하면, 동일 버전의 재설치나 번들 복구로 projection 메서드가 다시 제공되어도 persisted unsupported 억제가 해제되지 않는다.
- **근거**: 판정 0은 저장된 `blocked_capability_sig`와 현재 서명이 같으면 DB 조회와 capability probe 자체를 생략한다. 예를 들어 불완전한 PyInstaller 번들로 메서드 부재가 기록된 뒤 같은 앱 버전의 정상 번들을 재설치하면 버전 기반 서명은 그대로이므로, 실제 API가 복구됐어도 24시간 예외까지 적용된 채 영구 차단될 수 있다. “capability_sig 변화로만 재검증”한다는 현재 규칙에는 수동 복구 경로도 명시되지 않았다.
- **대안**: capability 서명에 실제 메서드 존재 여부 또는 배포 산출물의 build ID/manifest hash를 포함하거나, 앱 설치·업데이트 시 unsupported 메타만 명시적으로 무효화한다. 최소한 UI에 “지금 다시 확인” 기능이나 sidecar의 unsupported 상태를 안전하게 초기화하는 운영 절차를 제공할 수 있다.

### [m-1] Windows 피크 메모리 수용 판정 방식이 충분히 정의되지 않음 (Minor)
- **관점**: 5. 성능
- **지적**: `PeakWorkingSetSize`를 필수 기록하도록 했지만 baseline과 어떤 방식으로 비교하고 최종 게이트에 어떻게 반영할지가 명확하지 않다.
- **근거**: `PeakWorkingSetSize`는 프로세스 수명 전체의 누적 피크라서 인터프리터 시작·모듈 import·DB open 단계의 피크를 포함하며 일반적으로 리셋할 수 없다. 반면 확정 기준인 중앙값 30MB·개별 60MB는 `max(sampled_rss)-baseline_rss` 형태로 설명되어 있어, 두 측정치가 불일치할 때 합격 여부가 모호하다.
- **대안**: 확정 게이트는 psutil delta에 적용한다고 명시하고 OS 피크는 보조 교차 검증으로 정의하거나, 별도 측정 프로세스에서 DB open까지의 baseline lifetime peak와 시험 프로세스의 peak를 비교할 수 있는 통제된 절차를 정의한다. 불일치 허용 범위와 불합격 조건도 함께 고정하는 편이 좋다.

### [m-2] dirty marker 테스트 설명이 최대 1초 join 계약과 불일치 (Minor)
- **관점**: 1. 요구사항 누락, 8. 장애 대응
- **지적**: A-0001 검증 계획은 `clear_dirty_shutdown`의 “비동기 즉시 반환”을 테스트한다고 쓰지만, 실패 모드에서는 daemon 스레드 시작 후 최대 1초 `join()`하도록 최종 설계가 변경돼 있다.
- **근거**: 같은 문서 안에서 리뷰12의 즉시 반환 표현과 리뷰14의 bounded join 계약이 함께 남아 있다. 이 상태에서는 테스트가 반환 시간 0에 가까운 동작을 요구하는지, 1초 상한만 검증하는지 해석이 갈린다.
- **대안**: 검증 계획을 “삭제 스레드를 시작하고 최대 `_CLEAR_DIRTY_JOIN_TIMEOUT_SEC`까지만 기다리며, 미완료여도 반환한다”로 수정하고, 빠른 완료·타임아웃·예외 세 경우를 테스트하도록 명시한다.

### [N-1] 유휴 시 DB 조회 0회라는 결과 표현이 강제 reconciliation과 모순 (Nit)
- **관점**: 1. 요구사항 누락
- **지적**: ADR 결과의 “유휴 방치 중 purge의 DB 조회가 0회”는 최초 실행과 24시간 강제 reconciliation을 고려하면 절대적인 보장이 아니다.
- **근거**: 같은 문서에서 변경이 없어도 기본 24시간마다 한 번 purge를 실행한다고 명시한다.
- **대안**: “대부분의 유휴 사이클에서 0회이며, 최초 실행·메타 손상·24시간 강제 reconciliation 시에는 projection 조회 1회”로 표현을 정정한다.

## 확인 필요
- `requirements.md`의 R-0002 원문이 제공되지 않아 FR-3의 대량삭제 차단 예외와 NFR-1의 확정 메모리 기준이 실제 승인 요구사항과 정확히 일치하는지는 확인 필요하다.
- sidecar 저장 실패 후에도 “현 프로세스에서 정상 스킵·억제 상태가 지속된다”는 보장은 `_purge_meta_cache`를 소유한 `CollectorWorker` 인스턴스가 사이클 사이에도 재사용된다는 전제에 의존한다. 워커가 매 사이클 새로 생성된다면 프로세스 내 보장이 성립하지 않으므로 실제 객체 수명과 캐시 소유 위치를 확인해야 한다.
