## 총평
projection과 조건부 스킵을 함께 적용한 방향은 원인 제거와 유휴 비용 억제를 동시에 달성하며, 상태 전이·실패 억제·메타 손상 처리도 전반적으로 구체적이다. 특히 성공 스킵보다 차단·백오프를 우선하고 실패 시 `reconciled_sig`를 해제한 결정은 재시도 기아를 방지한다. 배포 버전 고정과 성능 수용 절차까지 마련되어 현재 진행을 막을 결함은 보이지 않는다. 다만 projection API capability 판정 범위와 리뷰 추적 정보에는 보완이 필요하다.

**판정**: APPROVE_WITH_CHANGES

## 동의하는 결정
- 전체 테이블 로드 대신 `file_path` projection을 사용하면서 정상 유휴 사이클에서는 DB 조회 자체를 생략한 것은 문제의 직접 원인과 반복 빈도를 모두 줄이는 적절한 설계다.
- 차단 → 백오프 → 성공 스킵 → 실행 순서와 실패·unsupported 시 `reconciled_sig`를 해제하는 상태 전이에 동의한다. 이전 성공 상태가 실패 후 재시도를 가리는 경쟁을 명시적으로 차단한다.
- sidecar를 기존 `index_state.json`과 분리하고, 저장 실패와 무관하게 프로세스 내 상태를 즉시 반영하되 재시작 후 보수적으로 재실행하는 정책은 호환성·운영 비용·멱등성을 균형 있게 고려했다.
- `lancedb==0.34.0` 정확 고정과 독립 프로세스·독립 DB 복제 기반 성능 시험은 재현성과 결과 오염 방지 측면에서 타당하다.
- 경로 서명과 소속 판정이 동일한 정규화 결과를 사용하고 경계 인식 비교를 적용한 것은 서명과 실제 삭제 판정의 불일치를 방지한다.

## 지적 사항

### [m-1] capability probe가 `to_arrow` 메서드 부재를 영구 비호환으로 식별하지 못함 (Minor)
- **관점**: 8. 장애 대응
- **지적**: `"unsupported"` 판정은 `table.search`와 `search().select`의 존재 여부만 확인하며, projection 호출 체인의 필수 메서드인 builder의 `to_arrow` 존재 여부는 probe 대상에 포함되지 않았다.
- **근거**: 문서는 메서드 자체가 없는 영구 장애와 호출 도중의 내부 예외를 구분하는 것을 핵심 정책으로 삼지만, `select()` 결과에 `to_arrow`가 없는 경우는 명백한 정적 capability 부재임에도 `"failed"`로 분류되어 30분 백오프를 무기한 반복하게 된다. 정확 버전 고정으로 발생 가능성은 낮지만, 비정상 번들이 실제 배포되면 이미 감지 가능한 영구 장애를 반복 실패로 처리한다.
- **대안**: `search()` 호출 자체의 예외는 `"failed"`로 유지하되, 정상적으로 얻은 search builder의 `select`와 정상적으로 얻은 select builder의 `to_arrow`를 각각 `getattr`+`callable`로 검사한다. 이 정적 메서드 부재만 `"unsupported"`로 분류하고, 각 메서드 호출 중 발생한 예외는 계속 `"failed"`로 분류한다.

### [m-2] Accepted 상태의 리뷰 추적 정보가 실제 문서 내용과 불일치함 (Minor)
- **관점**: 8. 장애 대응
- **지적**: ADR 상단과 architecture.md 리뷰 이력은 17차 리뷰를 최종 승인 근거로 기록하지만, 본문에는 설계 리뷰 19차·20차에서 결정된 내용이 포함되어 있다.
- **근거**: ADR 상태 표는 “1~17차 전건 처리”라고 쓰고 architecture.md의 리뷰 이력도 17차에서 끝난다. 반면 ADR 결과와 A-0002 실패 모드는 리뷰19 M-2 및 리뷰20 M-1을 근거로 정확 버전 고정 정책을 설명한다. 따라서 현재 Accepted 스냅샷의 최종 검증 범위와 미종결 항목 유무를 문서만으로 추적할 수 없다.
- **대안**: ADR 상태 표와 architecture.md 리뷰 이력에 18~20차 결과, 판정, 항목 처리 결과를 추가하고 실제 리뷰 파일 경로를 연결한다. 18차가 없거나 번호가 다른 경우에는 실제 리뷰 식별자에 맞게 본문 참조 번호를 정정한다.

## 확인 필요
- 대응 요구사항 원문인 `requirements.md`의 R-0002가 리뷰 대상에 포함되지 않아, 24시간 reconciliation 예외와 대량삭제 차단의 수동 해제 정책이 승인된 FR/NFR 문언과 정확히 일치하는지는 확인 필요하다.
- 소스 코드가 제공되지 않아 `search()` 또는 `select()` 호출 중 발생한 예외가 실제로 `"failed"` 경로에 들어가는지, 그리고 sidecar 전이마다 상호 배타적 필드가 완전히 초기화되는지는 구현 확인이 필요하다.
