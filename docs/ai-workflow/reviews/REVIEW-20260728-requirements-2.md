## 총평
두 요구 블록 모두 실제 베타 장애를 재현 가능한 시나리오와 시간 기준으로 구체화했고, 특히 종료 경로를 워커 상태별로 분리하고 purge의 조용한 전체 로드 폴백을 금지한 결정은 타당하다. 다만 R-0001은 데이터 무결성 NFR와 강제 종료 후 복구 가능성을 검증하는 수용 기준이 없고, R-0002는 purge 재실행 조건의 문언이 `op_sig` 기준과 일치하지 않는다. 또한 O(1) 및 메모리 상한의 측정 범위와 지속 상태의 재시작·시계 변경 의미를 명확히 해야 구현과 테스트가 서로 다른 해석으로 갈리는 것을 막을 수 있다. 핵심 방향을 바꿀 필요는 없지만 요구사항의 검증 가능성을 보완한 뒤 확정하는 것이 적절하다.

**판정**: APPROVE_WITH_CHANGES

## 동의하는 결정
- R-0001에서 창 표시 여부와 워커 상태를 별도 축으로 나누고, 유휴·정상 인덱싱·행오버 종료에 각각 시간 상한을 둔 것은 재현과 회귀 검증에 적합하다.
- 기존 `stop_worker` 호출부 호환을 유지하면서 반환값 추가는 허용하도록 stale 제약을 정정한 결정에 동의한다. 기존 호출자가 반환값을 무시할 수 있으므로 요구의 본래 의도와 일치한다.
- R-0002에서 projection 미지원 버전에 조용히 전체 로드로 폴백하지 않고 배포를 차단한 것은 상주 프로세스의 메모리 회귀를 방지하는 올바른 fail-fast 정책이다.
- 주기적 reconciliation, 일시 장애 백오프, 대량삭제 차단을 구분한 것은 성능 최적화가 기존 정합성·삭제 안전장치를 약화하지 않도록 한 합리적인 결정이다.
- 벡터 및 암호문이 결과에서만 제거되는 가짜 projection까지 AC-1에서 배제한 점은 성능 요구를 실제 스캔 비용까지 검증하려는 좋은 기준이다.

## 지적 사항

### [M-1] 정상 종료 데이터 무결성과 강제 종료 후 복구가 수용 기준에 없음 (Major)
- **관점**: 1. 요구사항 누락, 7. 동시성, 8. 장애 대응
- **지적**: R-0001 NFR-1은 “state 저장·스케줄러 정지 후 종료”를 요구하지만 이를 검증하는 AC가 없다. 또한 FR-4와 AC-3b는 `terminate` 및 하드 종료를 허용하면서, LanceDB/state 저장 도중 강제 종료된 경우 다음 실행에서 무엇이 관측되어야 하는지 정의하지 않는다.
- **근거**: AC-1~AC-3b는 프로세스 종료 시간만 확인하고 AC-4는 포괄적인 pytest 통과만 요구한다. 따라서 프로세스는 시간 안에 끝나지만 정상 경로에서 state 저장을 누락하거나, 강제 종료 후 사용자에게 아무 신호도 주지 않는 구현도 문언상 통과할 수 있다.
- **대안**:
  1. 정상 종료 AC를 추가해 스케줄러 중지, state 저장 완료, 워커 종료, Qt 종료 호출 순서 또는 이에 해당하는 관측 결과를 스파이 테스트로 검증한다.
  2. 강제 종료의 데이터 보장 범위를 명시한다. 예를 들어 인덱스는 재생성 가능한 파생 데이터로 간주하되, 다음 실행 시 비정상 종료 표식·경고가 노출되고 수동 재인덱싱 복구 경로가 제공됨을 AC로 둔다.
  3. 최소한 강제 종료 중 사용자 원본 문서와 설정/state 중 어느 데이터까지 무결성을 보장하는지 명시적으로 구분한다.

### [M-2] purge 즉시 실행 조건과 `op_sig` 기반 스킵 조건이 불일치함 (Major)
- **관점**: 1. 요구사항 누락, 2. 숨은 가정
- **지적**: FR-3의 “구성·설정 변경”은 모든 설정 변경으로 읽히지만, AC-2는 `op_sig` 불변 여부만 스킵 조건으로 사용한다. 어떤 설정이 purge 관련 구성인지 정의되지 않아 구현과 테스트의 재실행 조건이 달라질 수 있다.
- **근거**: 관련 없는 LLM 설정만 바뀐 경우에도 FR-3의 문자적 의미로는 purge를 즉시 실행해야 한다. 반대로 watch folder나 삭제 차단율처럼 purge 결과에 직접 영향을 주는 값은 반드시 즉시 실행되어야 한다. 대량삭제 차단 후 “구성·차단율을 바꿔야 재실행”한다는 문언도 어떤 구성 변경이 차단을 해제하는지 같은 모호성을 가진다.
- **대안**: `op_sig`를 구성하는 purge 관련 입력을 요구사항에 명시한다. 예를 들어 정규화된 `watch_folders`, `dry_run`, `max_delete_ratio`만 포함하고, FR-3을 “purge 관련 구성(`op_sig` 구성요소) 또는 파일 변경”으로 수정한다. 각 구성요소 변경과 파일 변경 시 즉시 1회 조회하는 AC도 추가한다.

### [M-3] 재시작 및 시스템 시계 변경 시 purge 억제 상태의 의미가 정의되지 않음 (Major)
- **관점**: 2. 숨은 가정, 7. 동시성, 8. 장애 대응
- **지적**: 마지막 성공 시각, 실패 백오프, 대량삭제 차단 상태가 프로세스 재시작 후에도 유지되어야 하는지 명확하지 않다. 또한 벽시계가 뒤로 이동하거나 저장 상태가 손상·유실된 경우의 보수적 동작도 정의되지 않았다.
- **근거**: FR-3은 “동일 설정으로는 재시도하지 않는다”, “최대 24시간 이내에 시도한다”고 표현해 프로세스 수명을 넘어서는 보장을 암시한다. 그러나 AC-2와 AC-4는 동일 프로세스 내 반복 사이클만으로도 통과할 수 있어, 재시작마다 전건 조회하거나 차단 상태를 잊는 구현을 걸러내지 못한다.
- **대안**:
  1. 성공·실패·차단 메타의 지속성 범위를 명시하고 재시작 테스트를 추가한다.
  2. 메타가 없거나 손상된 경우에는 안전하게 purge를 재실행하되 대량삭제 차단기는 그대로 적용한다고 정의한다.
  3. 시계 역행 시 즉시 재검증 또는 최대 대기 상한 적용 등 한 가지 정책을 정하고 테스트한다.
  4. “동일 설정으로 재시도하지 않음”이 앱 재시작 후에도 유지되는지 명시적으로 결정한다.

### [M-4] 성능 NFR의 범위와 수치가 객관적으로 판정하기 어려움 (Major)
- **관점**: 4. 확장성, 5. 성능
- **지적**: “스킵되는 일반 유휴 사이클은 O(1)”이 전체 인덱싱 사이클을 뜻하는지 purge 판단 경로만 뜻하는지 불명확하며, “추가 할당 수십 MB 이내”도 정확한 상한과 측정법이 없다.
- **근거**: 일반 유휴 사이클은 파일 변경 탐지를 위한 폴더 스캔 등 다른 O(N) 작업을 포함할 수 있으므로 전체 사이클 O(1)은 달성 불가능할 수 있다. 또한 “수십 MB”는 20MiB, 50MiB, 90MiB 중 어디까지 허용하는지 판정할 수 없고 RSS, Python 추적 메모리, Arrow allocator peak 중 무엇을 측정하는지도 정해지지 않았다.
- **대안**:
  1. NFR-1을 “purge 판단 및 DB 조회 경로는 watch folder 수에 대해서만 O(W), DB 행 수 N과 무관하며 DB 스캔 0회”처럼 범위를 제한한다.
  2. 10만 청크 기준 peak 추가 할당을 구체적인 값으로 정하고, RSS 또는 Arrow allocator 등 측정 지표·측정 구간·반복 횟수·허용 오차를 명시한다.
  3. 경로 길이와 중복 경로 수 등 벤치마크 데이터 조건도 고정한다.

### [m-1] R-0001 종료 경로 테스트 매트릭스가 충분히 명시되지 않음 (Minor)
- **관점**: 7. 동시성, 8. 장애 대응
- **지적**: AC-4의 “사외(pytest) 종료 경로 단위 테스트 통과”만으로는 FR-1~FR-4의 모든 분기와 중복 종료 요청에 대한 테스트가 보장되지 않는다.
- **근거**: 트레이 종료, `close_action=quit`, 워커 미실행, 정상 취소, `terminate`, 하드 종료, `isRunning()` 조회 예외는 서로 다른 분기다. 근접한 트레이 종료와 창 닫기 요청이 들어왔을 때 종료 정리가 중복 실행되는지도 현재 AC에는 없다.
- **대안**: AC-4에 최소 매트릭스를 열거하고, 종료 처리의 멱등성 및 각 분기에서 quit/hard-exit 중 정확히 하나만 호출됨을 검증하도록 구체화한다.

### [m-2] 문서 전체 상태와 개별 요구 상태의 의미가 불명확함 (Minor)
- **관점**: 9. 운영 복잡도
- **지적**: 문서 상단 상태는 `Draft`인데 R-0001과 R-0002는 모두 `Approved`다. 블록별 승인 모델이라면 문서 전체 상태가 무엇을 나타내는지 설명이 필요하다.
- **근거**: 상단 사용법은 상태가 Draft에서 Approved로 전환된다고 설명하지만, 실제 운영 단위가 파일인지 요구 블록인지 명확하지 않아 자동화나 리뷰어가 승인 상태를 다르게 해석할 수 있다.
- **대안**: 상단 상태를 문서 템플릿 자체의 상태로 정의하거나 제거하고 블록 상태만 정본으로 삼는다. 파일 내 모든 활성 블록이 승인되면 상단도 Approved로 맞추는 규칙을 둘 수도 있다.

## 확인 필요
- R-0001의 “정상 인덱싱”이 취소 플래그를 제한 시간 안에 관측할 수 있는 상태만 뜻하는지, 비-COM API 호출 등에서 블로킹된 상태도 포함하는지 확인 필요.
- 대량삭제 차단 상태가 앱 재시작 후에도 동일 설정에서는 유지되어야 하는지 확인 필요.
- R-0002의 “파일 변경이 있는 사이클”이 실제 신규·수정·삭제 처리 건수가 1건 이상인 경우인지, 스캔 중 감지만 되었으나 백오프·오류 등으로 처리되지 않은 경우도 포함하는지 확인 필요.
- 10만 청크 메모리 상한 측정 대상이 프로세스 RSS, Python heap, Arrow allocator 중 무엇인지 확인 필요.
