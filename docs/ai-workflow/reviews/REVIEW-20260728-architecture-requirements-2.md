## 총평
A-0003의 원인축과 누적축 분리, 양성 증거 기반 암호 판별, 승격 후 안전밸브 유지 방향은 기존 백오프 이력을 보존하는 합리적인 설계다. 다만 기존 승인 요구인 R-0001의 인터페이스 불변 제약과 A-0001의 구현 계약이 직접 충돌해 문서 정합성이 깨져 있다. 또한 A-0003의 CFB 판별 방식은 첫 디렉터리 섹터만 읽는 것으로 기술되어 정상적인 암호화 OOXML을 놓칠 수 있으므로 AC-4를 일반적으로 보장하지 못한다. 암호 판별의 우선순위와 네트워크 파일 I/O 행오버도 구현 전에 명확히 해야 한다.

**판정**: REQUEST_CHANGES

## 동의하는 결정
- `OPEN_ERROR_REPEATED`를 별도 `kind`로 저장하지 않고 원인과 누적 상태를 분리한 결정에 동의한다. 기존 `note_failure()`의 kind 변경 시 카운터 초기화 규칙과 충돌하지 않으며, #68과 같은 백오프 후퇴를 구조적으로 피한다.
- 암호 보호를 단순 OLE2 매직이나 HRESULT가 아니라 `EncryptedPackage`와 `EncryptionInfo`라는 양성 증거로 판별하고, 음성 증거만으로 DRM을 확정하지 않는 결정은 오분류 방지 측면에서 타당하다.
- 승격 상태에서도 7일 안전밸브, 파일 변경, 수동 재시도로 다시 시도하게 한 것은 “조용한 영구 미인덱싱”을 막는 적절한 장애 대응이다.
- 라우팅부터 sidecar 기록까지 통과하는 통합 테스트와 오라벨 회귀 픽스처를 요구한 검증 계획에 동의한다. 분류 함수 단위 테스트만으로는 실제 reader 선택과 실패 정보 전달을 검증할 수 없다.
- R-0003과 A-0003을 모두 Draft로 유지하고 사람 승인 전 구현하지 않는다는 범위 통제는 문서화되어 있어 적절하다.

## 지적 사항

### [B-1] R-0001의 인터페이스 불변 제약과 A-0001의 반환 계약 변경이 충돌함 (Blocker)
- **관점**: 1. 요구사항 누락
- **지적**: R-0001은 제약으로 “기존 `stop_worker` 인터페이스 불변”을 명시하지만, A-0001은 `stop_worker()`가 `terminate()` 사용 여부를 `bool`로 반환하도록 **반환값 계약을 변경**했다고 명시한다. 두 승인 문서를 동시에 만족할 수 없다.
- **근거**: `requirements.md` R-0001 제약과 `architecture.md` A-0001 컴포넌트 표 및 리뷰15 대응 내용이 정면으로 상충한다. Python에서 기존 호출자가 반환값을 무시할 수 있더라도, 문서가 명시한 인터페이스 계약 자체는 변경된 것이다.
- **대안**: 
  1. 실제 의도가 “기존 호출 방식과의 호환 유지”였다면 R-0001 제약을 그 문언으로 수정하고 사람 승인 이력을 남긴다.
  2. 문자 그대로 인터페이스 불변이 필요하다면 기존 `stop_worker()`는 유지하고, 결과가 필요한 새 API인 `stop_worker_with_outcome()` 또는 결과 객체를 반환하는 별도 내부 함수를 도입한다.
  3. 어느 쪽이든 A-0001/R-0001/ADR-0001의 계약을 동일하게 맞춘 뒤 Accepted 상태를 재확인한다.

### [B-2] 첫 디렉터리 섹터만 보는 CFB 판별은 암호화 OOXML을 완전하게 식별하지 못함 (Blocker)
- **관점**: 1. 요구사항 누락, 2. 숨은 가정, 6. 보안
- **지적**: A-0003은 CFB 헤더의 첫 디렉터리 섹터를 읽어 두 스트림 이름을 찾는 것으로 설명한다. CFB 디렉터리는 여러 섹터로 이어질 수 있으므로, 필요한 엔트리가 첫 섹터 밖에 있으면 정상적인 암호 보호 OOXML을 `PASSWORD_PROTECTED`로 판별하지 못한다.
- **근거**: R-0003 FR-3과 AC-4는 암호 보호 `.xlsx`의 별도 분류를 요구하지만, 설계 §3은 “첫 디렉터리 섹터를 읽고” 확인한다고 한정한다. CFB의 디렉터리 스트림 위치와 길이는 FAT 체인을 따라야 하며 섹터 크기도 512바이트로 고정되지 않는다. “필요한 파싱이 30줄 수준”이라는 판단에는 정상 CFB 변형과 손상 입력 처리에 대한 근거도 없다.
- **대안**:
  1. 검증된 CFB 파서를 사용하고, 폐쇄망 의존성 문제는 빌드 의존성 고정 또는 검토된 코드의 vendoring으로 해결한다.
  2. 직접 구현해야 한다면 sector shift, FAT/DIFAT, 디렉터리 체인, 순환·범위 초과 sector ID, 파일 크기 검증을 포함한 **읽기 상한 내 bounded traversal**을 명세한다. 첫 섹터 밖에 두 스트림이 배치된 픽스처, 4096바이트 섹터 CFB, 순환·절단된 체인을 반드시 테스트한다.
  3. 64KB 상한 때문에 일부 합법 파일을 판별하지 못할 수 있다면 이를 명시적으로 `UNKNOWN/UNRECOGNIZED` 처리하고, AC-4의 보장 범위도 동일하게 한정해야 한다.

### [M-1] 워치독 판정이 양성 암호 증거보다 먼저 적용됨 (Major)
- **관점**: 1. 요구사항 누락, 2. 숨은 가정
- **지적**: 데이터 흐름은 워치독이 발화하면 즉시 `OPEN_TIMEOUT` 또는 `READ_TIMEOUT`으로 반환하고, 컨테이너 판별은 워치독 미발화 경로에서만 수행한다. 따라서 암호 보호 OOXML이 Open 과정에서 행오버되어 워치독이 발화하면 양성 증거가 있어도 `PASSWORD_PROTECTED`가 되지 않는다.
- **근거**: R-0003 FR-3과 AC-4에는 “워치독 미발화 시에만”이라는 제한이 없지만, A-0003의 분류 순서는 이를 암묵적으로 추가한다. 현재 더미 암호가 보통 즉시 실패한다는 사실만으로 모든 Office·DRM·파일 상태에서 타임아웃이 없다고 보장할 수 없다.
- **대안**: 실패한 OOXML에 대해서는 워치독 발화 여부와 무관하게 bounded signature probe를 수행하고, 확실한 `PASSWORD_PROTECTED` 증거가 있으면 timeout보다 우선하도록 분류 우선순위를 정한다. 반대로 timeout을 우선해야 한다면 그 이유와 AC-4의 적용 범위를 요구사항에 명시한다.

### [M-2] 반복·조치 필요 상태의 단일 파생 모델이 명확하지 않음 (Major)
- **관점**: 3. 아키텍처 결함, 9. 운영 복잡도
- **지적**: 컴포넌트 표에는 `FailureRecord.escalated`라는 파생 속성 하나만 추가한다고 되어 있지만, 실제 정책은 `일반`, `반복 중`, `사용자 조치 필요`의 세 상태를 필요로 한다. UI와 백오프가 각각 `consecutive_failures`와 설정 임계값을 해석하면 상태 판정이 중복되어 서로 다른 결과를 낼 수 있다.
- **근거**: §5는 2회와 3회를 서로 다른 UI 상태로 정의하고 두 임계값을 config화한다. 한편 `app/bridge.py`는 화면 변환을, `backoff_seconds()`는 승격 분기를 각각 담당한다. 단순 boolean `escalated`만으로는 2회 “반복 중”과 3회 “조치 필요”를 모두 표현할 수 없다.
- **대안**: `escalation_state(record, policy) -> NORMAL | REPEATED | NEEDS_USER_ACTION` 같은 단일 순수 함수를 `failure_state`에 두고 UI와 백오프가 모두 사용하게 한다. `repeat_at < action_at`, 양의 정수, bool 제외 같은 config 교차 검증 규칙도 함께 명세하고 테스트한다.

### [M-3] 64KB 읽기 상한은 네트워크 파일 I/O의 시간 상한을 보장하지 않음 (Major)
- **관점**: 2. 숨은 가정, 8. 장애 대응
- **지적**: 읽는 바이트 수를 64KB로 제한해도 SMB 또는 DRM 드라이브의 `open`, `seek`, `read` 자체가 장시간 블록될 수 있다. 현재 실패 모드는 예외 발생만 다루며, 판별 I/O가 반환하지 않는 경우를 다루지 않는다.
- **근거**: 프로젝트는 일반 SMB와 DRM 드라이브를 지원하고, 기존 COM 행오버도 별도 워치독을 둘 정도로 블로킹이 실제 운영 위험이다. 컨테이너 판별은 COM 실패 후 수행되므로 기존 COM 워치독이 이미 해제된 뒤일 가능성이 높고, 이 단계가 멈추면 수집기 QThread 전체가 다시 행오버된다.
- **대안**:
  1. reader 라우팅 단계에서 이미 읽은 시그니처/헤더를 사이클 범위 캐시로 전달해 추가 reopen을 최소화한다.
  2. 네트워크 경로에서는 판별 실패를 허용하는 정책과 시간 예산을 명시하고, 예산을 강제할 수 없는 동기 I/O라면 해당 경로의 enrichment를 생략한다.
  3. 별도 격리 실행 단위를 사용한다면 타임아웃 후 안전하게 폐기할 수 있어야 하며, 단순 daemon 스레드 생성은 누적 행오버를 만들 수 있으므로 피한다.
  4. 최소한 “signature probe 행오버 → 종료 에스컬레이션” 시나리오를 실패 모드와 실기 테스트에 추가한다.

### [N-1] 문서 내 불필요한 빈 코드 블록과 AC 번호 순서가 가독성을 저해함 (Nit)
- **관점**: 9. 운영 복잡도
- **지적**: A-0003 라우팅 전제 뒤에 빈 fenced code block이 있고, R-0003 수용 기준은 AC-7이 AC-5·AC-6보다 먼저 배치되어 있다.
- **근거**: 기능상 결함은 아니지만 리뷰 추적과 요구-테스트 매핑 시 불필요한 혼동을 준다.
- **대안**: 빈 코드 블록을 제거하고 AC-1부터 AC-7까지 순서대로 정렬한다.

## 확인 필요
- 소스 코드가 제공되지 않아 `classify()` 호출이 실제로 COM 실패에만 한정되는지, `UnreadableFormatError → NEEDS_USER_ACTION` 및 기존 `FILE_CHANGED` 분기가 그대로 유지되는지는 확인할 수 없다.
- `SCHEMA_VERSION` 증가 시 기존 `index_failure.json`을 파일 전체 폐기하는지, 항목별 변환하는지, 알려진 기존 kind의 누적 횟수를 보존하는지 확인이 필요하다. FR-5는 안전한 폐기도 허용하지만 실제 동작과 테스트 기대값은 명시되어야 한다.

| N-1 | **수용** | 빈 fenced code block은 이전 편집 실수. 제거. AC는 AC-1~AC-7 순서로 재정렬하고, 6b 항목은 AC-8·AC-9로 분리 배치. |

### 확인 필요 항목에 대한 답

- **`classify()` 호출이 COM 실패에만 한정되는지 / 기존 분기 유지 여부**: 6a는 기존 분기
  (`UnreadableFormatError → NEEDS_USER_ACTION`, busy → `TEMPORARY_BUSY`, 워치독 → timeout)를
  **전부 유지**하고, 최종 폴백 직전에 `failed_stage` 분기만 삽입한다. 회귀 방어는 기존 테스트가
  담당한다.
- **`SCHEMA_VERSION` 증가 시 동작**: 파일 전체 폐기가 아니라 **알려진 kind는 보존, 미등록
  kind만 항목 단위 폐기**(기존 `load_failures` 동작 유지). 전체 폐기는 다른 원인의 유효한
  누적 이력까지 잃으므로 채택하지 않는다. A-0003 "남은 확인 사항" 5번에 기록, AC-6로 고정.
- **§5 승격 해석**: 사용자 확인 대기 중이라는 판단에 동의한다. **확인 전까지 정책값·UI 문구를
  확정하지 않는다**를 A-0003에 명시했다.

**종결 판정**: 이번 회차 Blocker 2 / Major 3 / Nit 1 중 —
**B-2·M-1·M-2·M-3·N-1 반영 완료**, **B-1은 별건 분리(Approved 문서 수정이라 사람 승인 필요)**.
6a 범위에 미종결 Blocker/Major는 없다. 단 사용자 확인 2건(승격 해석, R-0001 제약 수정)이
대기 중이므로 상태는 **Draft 유지**.
