## 총평
A-0001·A-0002는 실패 경로, 보수적 폴백, 성능 검증 기준까지 구체화되어 있으며 기존 결정의 근거도 충분히 추적 가능하다. A-0003 역시 원인축과 누적축을 분리하고, 위험한 컨테이너 판별을 6b로 이연한 방향은 타당하다. 다만 R-0001의 승인된 인터페이스 불변 제약과 A-0001의 구현 계약이 현재도 정면으로 충돌하며, A-0003에는 6a/6b 범위가 데이터 흐름·실패 모드·검증 계획에서 다시 혼재되어 있다. 또한 `TEMPORARY_BUSY`를 포함한 원인별 백오프와 원인 독립 승격 상태의 우선순위가 정의되지 않아 구현에 따라 재시도 정책이 크게 달라질 수 있다.

**판정**: REQUEST_CHANGES

## 동의하는 결정
- `OPEN_ERROR_REPEATED`를 원인 `kind`로 저장하지 않고 `consecutive_failures`에서 파생하는 결정에 동의한다. 원인 변경 시 카운터를 초기화하는 기존 규칙과 충돌하지 않으면서 반복 상태를 표현할 수 있다.
- 컨테이너 판별을 6b로 분리한 결정에 동의한다. CFB 파싱 복잡도와 네트워크 파일 I/O 행오버 위험을 고려하면, `failed_stage`만 사용하는 6a를 신규 I/O 없이 먼저 완결하는 것이 운영 위험과 구현 범위를 모두 줄인다.
- UI와 백오프가 `escalation_state()`라는 단일 판정 함수를 공유하도록 한 결정에 동의한다. 임계값 해석이 여러 호출부에 분산되는 것을 막는 적절한 단일 진실원이다.
- A-0001의 명시적 Qt 종료 모델과 A-0002의 projection·보수적 sidecar 처리 방향에 동의한다. 특히 하드 종료 경로에서 동기 파일 I/O와 로깅 flush를 제거한 점, purge 메타 손상 시 스킵하지 않는 점은 실패 안전성이 명확하다.

## 지적 사항

### [B-1] 승인된 `stop_worker` 인터페이스 불변 제약과 Accepted 설계가 충돌함 (Blocker)
- **관점**: 1. 요구사항 누락
- **지적**: R-0001은 제약으로 “기존 `stop_worker` 인터페이스 불변”을 명시하지만, A-0001은 `stop_worker()`가 `terminate()` 사용 여부를 `bool`로 반환하도록 계약을 변경했다고 명시한다. 승인된 요구와 Accepted 설계가 동시에 참일 수 없는 상태다.
- **근거**: `requirements.md` R-0001의 제약은 현재도 Approved 상태이며, `architecture.md` A-0001의 컴포넌트 표와 실패 모드는 반환값 변경 및 호출부 전파를 필수 안전장치로 정의한다. A-0003의 “남은 확인 사항”에서도 실재하는 모순이라고 확인했지만, 문서 정합성은 아직 복구되지 않았다.
- **대안**: 사람 승인을 받아 R-0001 제약을 “기존 호출 방식 호환 유지; 반환값 추가는 허용”처럼 실제 승인된 동작에 맞게 수정한다. 반환 계약 변경을 허용할 수 없다면 별도 결과 객체·상태 조회 API 등으로 강제 종료 여부를 전달하도록 A-0001을 재설계해야 하지만, 현재 구현과 안전성 근거를 보면 요구 문언을 정정하는 쪽이 더 단순하다.

### [M-1] A-0003의 6a와 6b 범위가 데이터 흐름에서 다시 혼재됨 (Major)
- **관점**: 1. 요구사항 누락
- **지적**: 범위 분할 표에서는 6a가 신규 I/O 없이 `OPEN_ERROR`/`READ_ERROR`와 승격만 구현한다고 선언했지만, A-0003의 주 데이터 흐름은 여전히 CFB 컨테이너 판별과 `PASSWORD_PROTECTED`·`UNRECOGNIZED_CONTAINER` 분류를 현재 흐름처럼 포함한다.
- **근거**: 컴포넌트 표에서는 `secure/signature.py`가 취소선으로 6b 이연되어 있고 R-0003 FR-3 및 AC-8·AC-9도 후속 범위로 표시된다. 반면 A-0003의 데이터 흐름, 실패 모드의 “시그니처 읽기 실패”, UI 검증의 `PASSWORD_PROTECTED`·`UNRECOGNIZED_CONTAINER` 항목은 6a 검증 계획과 구분되지 않는다. 구현자는 어느 부분이 이번 변경의 필수 동작인지 일관되게 해석할 수 없다.
- **대안**: A-0003의 본 데이터 흐름을 6a 전용으로 다시 작성하여 예외 타입/HRESULT/워치독/`failed_stage`만 포함하고, 6b 흐름은 “후속 개념안—구현 계약 아님” 하위 절로 완전히 분리한다. 실패 모드와 검증 계획도 각각 `6a 필수`와 `6b 후속`으로 나누고, 6a의 UI 테스트에서는 현재 구현되는 원인만 검증한다.

### [M-2] 원인별 백오프와 원인 독립 승격 상태의 우선순위가 불명확함 (Major)
- **관점**: 2. 숨은 가정
- **지적**: 문서는 승격을 `kind`와 독립적으로 판정하고 `backoff_seconds()`도 `escalation_state()`를 사용한다고 하지만, 동시에 `TEMPORARY_BUSY`는 자체 해소 가능성이 높아 5~10분 재시도를 유지해야 한다고 설명한다. 반복된 `TEMPORARY_BUSY`가 `NEEDS_ACTION`에 도달했을 때 5~10분을 유지하는지, 24시간/7일 사다리로 전환하는지 정의되지 않았다.
- **근거**: A-0003 결정 2는 `TEMPORARY_BUSY`를 OPEN_ERROR와 합치면 최대 30분 지연되는 것이 회귀라고 설명한다. 반면 결정 5의 표는 원인 구분 없이 1회 30분, 2회 6시간, 3회 24시간, 4회 이상 7일을 제시하며, 컴포넌트 표는 백오프가 승격 상태를 사용한다고 한다. 이대로면 UI 상태만 승격시키는 구현과 실제 대기 시간까지 승격시키는 구현이 모두 문서에 부합한다고 해석될 수 있다.
- **대안**: 원인별 정책 우선순위를 명시한 결정표를 추가한다. 예를 들어 `escalation_state()`는 모든 원인에 공통으로 UI 상태만 계산하되, `backoff_seconds()`는 `TEMPORARY_BUSY`에 대해 항상 기존 5~10분 정책을 우선하고 OPEN/READ 계열만 사다리를 사용하도록 분리할 수 있다. 반대로 3회 이후 busy도 7일로 늦추려는 의도라면 R-0003과 기존 정책의 변경임을 명시하고 별도 수용 기준을 추가해야 한다.

### [M-3] 핵심 승격 정책이 미확정인데 검증 계획은 확정값을 전제함 (Major)
- **관점**: 1. 요구사항 누락
- **지적**: A-0003은 “3회 = 사용자 조치 필요”가 UI 상태만 의미하는지, 3회차부터 7일 백오프까지 의미하는지 사용자 확인 전에는 정책값과 UI 문구를 확정하지 않는다고 한다. 그러나 검증 계획과 정책표는 이미 1/2/3/4회 경계 및 30분/6시간/24시간/7일을 확정된 계약처럼 사용한다.
- **근거**: “핵심 결정 5”의 경고와 “남은 확인 사항 1”은 핵심 사용자 동작이 미결정임을 명시한다. 이 결정은 `backoff_seconds()`, UI 표시, config 기본값 및 AC-2·AC-5 결과를 직접 바꾸므로 구현 직전의 단순 문구 확인이 아니다.
- **대안**: R-0003 승인 전에 두 해석 중 하나를 선택해 요구와 정책표를 함께 확정한다. 결정을 미룰 필요가 있다면 A-0003을 대안 A/B가 있는 탐색 설계로 유지하고, 구현·Reviewed 승격 조건에 “승격 의미 승인”을 명시하며 확정값 기반 테스트는 선택 이후의 검증 계획으로 표시한다.

### [m-1] 6a 실패 모드와 검증 항목에 후속 분류가 남아 있음 (Minor)
- **관점**: 8. 장애 대응
- **지적**: “시그니처 읽기 실패”는 신규 파일 I/O가 없는 6a에서는 발생하지 않는 실패 모드이며, UI 검증의 6b 분류도 이번 범위의 필수 검증처럼 읽힌다.
- **근거**: R-0003 NFR-1과 A-0003 범위 분할은 6a에 신규 파일 I/O가 없다고 명시한다. 그럼에도 A-0003 실패 모드 첫 행과 UI 변환 테스트에 6b 동작이 남아 있다.
- **대안**: 해당 실패 모드와 테스트를 6b 전용 절로 이동하고, 6a 실패 모드에는 `failed_stage` 누락·미등록 stage·비정상 escalation config·구 레코드 로드 등 실제 6a 경로만 둔다.

## 확인 필요
