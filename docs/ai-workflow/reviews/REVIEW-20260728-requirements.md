## 총평
두 요구 블록 모두 실제 베타 장애를 구체적인 재현 조건과 측정 가능한 종료 시간·메모리 기준으로 전환했으며, 기존 안전장치와의 호환성도 대체로 잘 명시했다. 특히 R-0002는 projection 미지원 시 조용히 전체 로드로 폴백하지 않는 결정과 장애 증폭 루프 방지를 요구 수준에서 고정한 점이 타당하다. 다만 강제 종료와 데이터 무결성의 경계가 불명확하고, “최대 24시간” 보장과 설정 가능 주기 사이에 판정 가능한 모순이 있다. 또한 O(1) 범위와 일부 운영 상태의 재시작 후 의미를 명확히 해야 구현·수용 테스트가 서로 다른 해석으로 갈리지 않는다.

**판정**: REQUEST_CHANGES

## 동의하는 결정
- R-0001에서 트레이 숨김, 창 표시, `close_action=quit`, COM 행오버를 각각 별도 경로로 구분하고 종료 시간 상한을 둔 것은 재현성과 회귀 방지 측면에서 적절하다.
- `stop_worker`의 반환값 추가를 허용하되 기존 호출부가 반환값을 무시해도 동작하도록 “호출 방식 호환”으로 제약을 정정한 결정에 동의한다. 승인된 동작과 stale 문언의 충돌을 제거했다.
- R-0002에서 projection 지원을 배포 전제조건으로 두고 미지원 버전에 전체 로드 폴백을 금지한 것은 성능 회귀를 숨기지 않는 올바른 fail-fast 정책이다.
- 일반 유휴 사이클은 조회를 생략하되 주기적 reconciliation, 구성 변경, 실패 백오프, 대량삭제 차단을 별도로 다룬 구조는 성능과 정합성·삭제 안전성을 균형 있게 반영한다.
- 벡터와 암호문이 단순히 결과에서 제거되는 것이 아니라 실제 스캔 단계에서 제외되는지 검증하도록 한 AC-1은 문제의 근본 원인을 직접 검증한다.

## 지적 사항

### [M-1] 강제 종료와 데이터 무결성 보장 범위가 불명확함 (Major)
- **관점**: 1. 요구사항 누락, 7. 동시성, 8. 장애 대응
- **지적**: NFR-1은 “정상 종료 시 데이터 무결성 유지”만 요구하지만, 어떤 시점까지를 정상 종료로 보는지와 `terminate` 또는 `os._exit`가 발생한 경우 허용되는 상태 및 복구 경로가 정의되지 않았다. FR-4는 강제 종료 에스컬레이션 유지를 명시하므로 두 요구의 경계를 판정 가능하게 만들어야 한다.
- **근거**: LanceDB 쓰기나 state 저장 중 강제 종료되면 스케줄러 정지만으로 데이터 무결성을 보장할 수 없다. 현재 AC-1~AC-4는 프로세스 종료 시간과 단위 테스트만 확인하며, graceful 경로에서 state 저장 및 스케줄러 정지가 완료되었는지 또는 강제 종료 이후 다음 실행에서 어떤 상태가 관측되어야 하는지는 검증하지 않는다.
- **대안**: NFR-1을 “워커가 graceful하게 정지한 경로에서는 state 저장 및 스케줄러 정지 완료 후 Qt 이벤트 루프를 종료한다”로 한정하고, 강제 종료 경로는 파생 인덱스 손상 가능성을 허용하는 예외로 명시한다. 이에 대응하여 정상 경로의 정리 순서·완료 여부를 검증하는 AC와, 강제 종료 발생 사실을 다음 실행에서 알리거나 재인덱싱 복구 절차를 제공하는 AC를 추가한다.

### [M-2] 24시간 상한과 설정 가능한 reconciliation 주기가 충돌함 (Major)
- **관점**: 1. 요구사항 누락, 2. 숨은 가정, 8. 장애 대응
- **지적**: FR-3은 정상 상태에서 불일치 복구를 최대 24시간 이내에 시도한다고 규정하면서 강제 reconciliation 주기를 config화한다. 그러나 설정값의 허용 범위와 오류 처리 정책이 없어 24시간을 초과하는 값이 입력될 경우 요구를 동시에 만족할 수 없다.
- **근거**: AC-2는 마지막 성공 purge 후 24시간이 지나면 조회가 발생한다고 고정하지만, 본문은 주기가 설정 가능하다고 한다. 예를 들어 설정값이 48시간이면 구현이 설정을 따르면 FR-3과 AC-2를 위반하고, 24시간으로 제한하면 사용자 설정을 따르지 않게 된다.
- **대안**: 다음 중 하나로 의미를 통일한다.
  1. 24시간을 절대 상한으로 유지하고 설정값을 `0 < value <= 86400`으로 검증하며, 초과값은 저장 거부 또는 86400으로 제한한다.
  2. 24시간을 기본값으로만 규정하고 FR-3과 AC-2를 “설정된 `purge_force_reconcile_sec` 이내”로 변경한다.  
  데이터 불일치 복구 SLA가 목적이라면 첫 번째 대안이 더 적합하다.

### [M-3] O(1) 요구의 측정 범위가 불명확함 (Major)
- **관점**: 2. 숨은 가정, 4. 확장성, 5. 성능
- **지적**: NFR-1의 “스킵되는 일반 유휴 사이클은 DB 조회 없이 O(1)”이 purge 판정만을 뜻하는지 전체 수집기 사이클을 뜻하는지 명확하지 않다.
- **근거**: 변경 0건을 알아내기 위한 watch folder 스캔 자체는 파일 수에 따라 일반적으로 O(N)이다. 현재 문언을 전체 유휴 사이클에 적용하면 구현 불가능하거나 기존 증분 스캔까지 범위에 포함되지만, 배경과 FR-2 및 AC-2는 purge DB 조회 제거만을 대상으로 한다.
- **대안**: “purge 실행 여부 판정은 감시 파일·청크 수와 무관하게 O(1)이며, 스킵 시 purge 목적의 LanceDB 조회·순회는 0회”로 범위를 좁힌다. 전체 수집기 스캔 비용은 이 요구의 비목표라고 명시해도 된다.

### [m-1] 대량삭제 차단 후 사용자 통지의 수용 기준이 없음 (Minor)
- **관점**: 1. 요구사항 누락, 8. 장애 대응
- **지적**: FR-3은 차단 발생 시 UI로 알리고 사용자가 구성 또는 차단율을 변경해야 재실행된다고 요구하지만, 이를 확인하는 수용 기준이 없다.
- **근거**: AC-4는 반복 전건 조회 방지와 백오프만 검증한다. 구현이 차단 상태를 내부적으로 영구 억제하면서 UI 알림을 누락해도 현재 AC는 통과할 수 있다.
- **대안**: “대량삭제 차단 시 삭제 및 동일 op_sig 재조회가 억제되고, UI에 차단 원인과 재실행 조건이 1회 이상 표시되며, watch folder 또는 차단율 변경 후 purge가 다시 시도된다”는 AC를 추가한다.

### [m-2] projection 배포 전제조건의 자동 검증 기준이 부족함 (Minor)
- **관점**: 1. 요구사항 누락, 8. 장애 대응, 9. 운영 복잡도
- **지적**: FR-1은 projection 지원 여부를 빌드·배포 전에 검증한다고 하지만, 어떤 버전 고정 또는 빌드 게이트로 배포를 차단할지 정의하지 않았다.
- **근거**: AC-1은 기능 검증에는 적합하지만, 배포 패키지의 실제 LanceDB 버전이 테스트 환경과 달라지는 경우를 막는 조건은 아니다. “미지원 버전에서는 배포하지 않는다”는 운영 요구를 수동 확인에만 의존할 가능성이 있다.
- **대안**: 배포 의존성 버전을 고정하고 해당 버전으로 실제 projection 스캔을 검증하는 테스트를 빌드 게이트에 포함한다. 또는 지원 버전 범위를 명시하고 패키징된 환경에서 AC-1 테스트가 실패하면 빌드를 실패시키도록 요구한다.

### [m-3] purge 메타데이터의 프로세스 재시작 후 의미가 정의되지 않음 (Minor)
- **관점**: 2. 숨은 가정, 7. 동시성, 8. 장애 대응
- **지적**: “마지막 성공 purge”, 실패 백오프, 대량삭제 차단 상태가 프로세스 재시작 후에도 유지되어야 하는지 명시되지 않았다.
- **근거**: 상태를 메모리에만 두면 앱 재시작 때마다 O(N) reconciliation이 실행되거나 실패·차단 억제가 초기화될 수 있다. 반대로 영속화하면 원자적 저장, 손상된 메타 처리, 시각 기준이 운영 요구가 된다. 현재 AC-2와 AC-4가 동일 프로세스 내 반복만 의미하는지 재시작까지 포함하는지 판단할 수 없다.
- **대안**: 정상 종료·재시작 후에도 마지막 성공 시각과 차단/백오프 상태를 유지할지 명시한다. 영속화를 요구한다면 원자적 저장과 손상 시 보수적 재실행을 AC에 포함하고, 영속화를 요구하지 않는다면 “재시작 직후 1회의 reconciliation은 허용”이라고 명시한다.

## 확인 필요
- R-0001의 “창이 보이는 상태에서 [종료]”가 트레이 메뉴의 [종료]를 뜻하는지, 별도의 창 내 종료 동작도 포함하는지 확인이 필요하다.
- R-0002의 “파일 변경이 있는 사이클”이 신규·수정·삭제·orphan 처리 중 무엇을 포함하는지, 단순 스캔 메타데이터 변화도 포함하는지 확인이 필요하다.
- 24시간 계산에 wall clock을 사용할지, 시스템 시각 역행·절전·재부팅 시 경과 시간을 어떻게 판정할지 확인이 필요하다.
