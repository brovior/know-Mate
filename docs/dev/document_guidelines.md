# 문서 작성 지침

> **위상:** 작업 지침(비규범). 보안·계약·동기화 의무는
> [`CLAUDE.md`](../../CLAUDE.md)가 우선한다. 문서의 현재 작업 상태는
> [`PLAN.md`](../PLAN.md)가 정본이다.

이 문서는 사람이 빠르게 읽고 Claude Code·Codex가 같은 행동을 선택할 수 있도록 문서를 쓰는
규칙이다. 새 규칙을 `CLAUDE.md`에 계속 추가하지 않는다. 세션마다 필요한 한 줄 위임만
`CLAUDE.md`에 둔다.

## 1. 기본 원칙

- **결론과 현재 행동을 먼저 쓴다.** 근거·대안·완료 이력은 뒤로 보낸다.
- 한 문단과 소제목에는 한 목적만 둔다. 현재 상태, 다음 행동, 과거 이력을 섞지 않는다.
- 명령·경로·라벨·수치는 모호한 표현 대신 정확한 값을 쓴다.
- 상세 설계나 긴 과거 설명을 여러 문서에 복사하지 않는다. 정본 문서 또는 Git 이력으로 링크한다.
- 경고·금지 사항은 관련 행동 바로 옆에 둔다. 독자가 여러 문단을 조합해야 다음 행동을 알게
  되는 구조를 만들지 않는다.
- 실데이터·SQL 원문·업무 데이터는 문서에 쓰지 않는다(`CLAUDE.md §2-1`).

### 1-1. 간결성은 의무다

문서는 가능한 짧게 쓴다. 길이는 친절함의 증거가 아니다. 독자가 행동을 선택하는 데 필요하지 않은
문장은 삭제한다.

- 같은 사실을 본문·표·인용문에 반복하지 않는다. 하나를 정본으로 두고 나머지는 링크한다.
- 한 문단에는 하나의 주장만 둔다. 조건이 둘 이상이면 문장을 나누거나 표로 바꾼다.
- “참고”, “주의”, “왜냐하면”, 과거 경위가 본문 흐름을 끊으면 부록 또는 Git 이력으로 옮긴다.
- 완료된 구현의 상세·과거 테스트 수·낡기 쉬운 코드 행 번호는 현행 작업 지시에서 제거한다.
- 긴 목록은 독자가 실제로 선택하거나 확인할 항목일 때만 쓴다. 단순 배경 설명을 목록으로 쪼개지
  않는다.
- 문장을 지운 뒤에도 현재 행동·제약·검증 기준이 남으면, 그 문장은 지운다.

### 1-2. 쉬운 말과 용어

- 독자가 알 필요가 없는 내부 약어·약칭·설계 별칭을 만들지 않는다.
- 전문 용어가 꼭 필요하면 첫 등장에 한 줄로 풀어 쓰고, 반복 설명 대신
  [`reference/glossary.md`](../reference/glossary.md) 또는 정본 계약으로 링크한다.
- 한국어로 바로 쓸 수 있으면 불필요한 영어·한자어·추상 명사를 쓰지 않는다.
- "처분", "배관", "계기판", "착지"처럼 프로젝트 안에서만 통하는 표현은 단독으로 쓰지 않는다.
  처음에는 실제 동작을 함께 쓴다. 예: "after 스냅샷 저장(결과 보존)".
- 확실하지 않은 사실은 단정적인 용어로 포장하지 않는다. `가설`, `미측정`, `보류`를 명시한다.

### 1-3. 주석·인용문·괄호 제한

주석은 본문보다 눈에 띄어야 할 **행동 제한**에만 쓴다. 설명을 보충하려는 습관으로 주석을 계속
붙이지 않는다.

- `>`, `⚠️`, `NOTE`, 괄호 설명은 다음 중 하나를 즉시 바꿀 때만 허용한다: 실행 금지, 보안 제한,
  데이터 손실 방지, 실패 조건, 비직관적인 예외.
- 같은 제한을 본문과 주석에 두 번 쓰지 않는다. 주석을 썼으면 본문은 짧게 연결한다.
- 한 행동에 경고는 하나만 둔다. 여러 경고가 필요하면 먼저 규칙 자체를 표나 체크리스트로
  재구성한다.
- 과거 논의, 구현 중 시행착오, “왜 이 문장이 생겼는지”는 주석으로 남기지 않는다. Git 이력이나
  부록으로 옮긴다.
- 코드 주석과 docstring도 같은 기준을 따른다. 코드만 읽어도 알 수 있는 사실, 예전 설계 절 번호,
  줄 번호, 테스트 단계 이름은 주석으로 남기지 않는다. 행동·불변식·놀라운 예외만 설명한다.
- 주석을 삭제해도 코드나 문서의 행동·제약·검증 방법이 바뀌지 않으면 삭제한다.

## 2. 문서의 역할을 먼저 정한다

새 문서를 만들기 전에 기존 문서로 충분한지 확인한다. 새 문서는 아래 역할 중 하나여야 한다.

| 역할 | 위치 | 내용 |
|---|---|---|
| 현행 계약 | `docs/spec/` | 지켜야 하는 규칙과 입출력 계약 |
| 현재 우선순위 | `docs/PLAN.md` | 다음 작업, 시작 조건, 완료 기준, 보류 사유 |
| 실행·판독 | `docs/guide/` | 명령, 환경 준비, 산출물 해설 |
| 개념·용어 | `docs/reference/` | 반복 참조할 설명과 용어 |
| 개발 작업 지침 | `docs/dev/` | 코드·문서 작성 시의 공통 작업 방식 |
| 임시 설계·조사 | `docs/wip/` | 진행 중 작업의 상세; 착지하면 정본 반영 후 삭제 |

어느 역할에도 맞지 않으면 대개 기존 문서의 한 절이나 코드 docstring으로 충분하다.

## 3. `PLAN.md` 작업 카드 형식

작업 카드는 다음 순서를 따른다. 모든 항목이 필요한 것은 아니지만, 독자가 첫 화면에서 현재
행동을 알아야 한다.

```text
목표
현재 상태
다음 행동
시작 조건·불변식
산출물
완료 기준
실측 후 또는 이후에 결정할 것
짧은 완료 이력
```

- 완료된 상세 구현은 작업 카드에서 한두 줄로 요약하고, 정본 계약·커밋 이력으로 연결한다.
- “다음”은 구현할 일과 사내 실측처럼 외부 조건이 필요한 일을 구분한다.
- 완료·미실행·보류를 명시한다. 과거 수치가 현재 조건과 다르면 현재 기대값처럼 쓰지 않는다.
- 작업 상태가 바뀌면 같은 커밋에서 갱신한다.

## 4. 설계 문서 형식

설계 문서는 현행 구현 지시와 설계 근거를 분리한다.

1. 첫 부분에는 현재 상태, 지금 구현할 범위, 하지 않을 범위를 둔다.
2. 구현 계약에는 불변식, 입력·출력, 실패 조건, 검증 기준만 둔다.
3. 완료된 단계의 상세 지시는 부록으로 옮기거나 현행 `docs/spec/`으로 연결한다.
4. 과거 코드 행 번호나 테스트 수는 빨리 낡으므로, 현재 행동을 지시하는 본문에 두지 않는다.
5. 미확인 분포·성능·효과는 가설로 표시하고 `SPEC.md`의 확정 수치와 섞지 않는다.

## 5. 정본과 링크

- 레이어 계약은 `docs/spec/` 한 곳에 둔다. WIP 절 번호를 코드·테스트의 장기 참조로 쓰지 않는다.
- 구조·용어·확정 실측치가 바뀌면 `SPEC.md`도 같은 커밋 또는 PR에서 갱신한다.
- 문서 링크는 실제 파일을 가리켜야 한다. 상대 경로와 Markdown 코드 블록 짝을 검증한다.
- 완료한 WIP 문서는 정본에 반영한 뒤 삭제하고 `docs/README.md` 색인에서도 제거한다.

## 6. 변경 전후 점검

문서 변경을 마치기 전에 확인한다.

- [ ] 문서의 역할과 정본 위치가 명확하다.
- [ ] 첫 화면에서 현재 상태와 다음 행동을 알 수 있다.
- [ ] 완료 이력과 현재 지시가 분리되어 있다.
- [ ] 같은 계약을 다른 말로 중복하지 않았다.
- [ ] 명령·경로·수치·링크가 실제와 맞다.
- [ ] 보안 불변식과 `docs/spec/`·`SPEC.md` 동기화 의무를 지켰다.
- [ ] Markdown 링크·표·코드 블록을 검증했고 `git diff --check`가 통과한다.
